# LESSONS.md — Why the template has these defaults

> These lessons were distilled from two projects that ran the harness, and ported into `loops` on 2026-10-06 from the predecessor harness v0.7.0 —
> project A, ~2 months (25 story packets, ~30 ADRs, 1 impartial cross-review), and project B (24 stories,
> 13 ADRs, many parallel sessions, ~41k lines of code). Four harvest rounds: the full docs review of 2026-08-18 → L15–L20;
> the round that built the parallel-run mechanism → L21–L23; **the technical review of 2026-09-04 (reading the code + running the gates with cache off, not just reading docs) → L24–L32**.
> The fourth: an independent review of the harness itself on 2026-09-28, reproducing the failures on a trial repo built from `template/` and comparing against project B → L33–L36 (now cases in `test/run.mjs`).
> Every counter-intuitive default traces back to a lesson that was paid for. **Do not change a default before reading its lesson.**

## What proved RIGHT (keep as is when using)

| # | Lesson | Encoded in |
| - | ------- | -------- |
| L1 | Two-way traceability actually works when commit messages carry the `(ST-xxx)`/`(ADR-xxxx)`/`(T-xxx)` id — the independent cross-review was able to confirm "every invariant boundary really has an ADR backing it" | LOOP.md rule 7; AGENTS.md boundary-must-have-an-ADR rule |
| L2 | The review → decision → doc update (version bump) loop actually runs, and it is the only learning mechanism that keeps the docs matching reality | The cross-review ritual in LOOP.md + templates/review.md |
| L3 | The backlog survives being re-cut mid-way (merging stories, splitting one in two, inserting a foundation story) without breaking the process — as long as IDs are stable and never reused | stories/README ID convention |
| L4 | The "land" pattern grew on its own outside the template: a story bigger than 1 PR always gets forced by reality into independently mergeable PRs — without this section in the template every team reinvents it | templates/story.md, Lands section |
| L5 | The intake → story → proof (tiny/normal/high-risk) chain kept the ceremony proportional to the risk across 25 consecutive stories | FEATURE_INTAKE.md kept nearly verbatim |

## What proved WRONG / had to be fixed by hand (the template's defaults changed accordingly)

| # | Lesson | Encoded in |
| - | ------- | -------- |
| L6 | A historical living doc (RETROSPECTIVE.md) was created and deleted by the PO **on the same day** — nobody wants to maintain it; per-doc changelogs + review snapshots are enough | No historical living doc is shipped; reviews/ are immutable snapshots |
| L7 | Tombstone creep: the agent kept spawning "(dropped)", "⏸ moved to a later phase" across the docs until the PO had to issue a "docs stay clean" rule mid-project | The no-tombstone rule written straight into LOOP.md rule 5 + AGENTS.md from day 0 |
| L8 | A rule in words is not enough: after the clean-docs rule existed, history still crept into the **status cells** of TEST_MATRIX and the backlog table | A strict cell convention written right in the TEST_MATRIX.md header |
| L9 | Story status duplicated in 2 places (backlog table + story file) → drift is guaranteed | The "one source of status" rule (LOOP.md rule 6; stories/README) |
| L10 | The "Common commands" section in AGENTS.md drifted from reality within a few weeks (dead commands still sitting in the doc) | Drift warning banner + pointer to the source of truth right in AGENTS.md |
| L11 | Immutable ADRs had no release valve: when scope got cut later, the ADR body still described a mechanism that was dead → risk of an agent implementing something that no longer exists | The "Drift notes" section in decisions/README.md |
| L12 | Good docs do not catch their own cross-contradictions (a Must depending on a Should, two definitions for the same day concept, orphan KPIs) — only one impartial cross-review caught them, after they had slipped through the whole docs layer | Cross-review promoted to a recurring ritual (LOOP.md) + the "Cross-consistency check" section in templates/review.md |
| L13 | ~1/3 of the backlog (8/25 stories) was **foundation discovered mid-way** that had to be inserted back "before ST-xxx": a real runtime skeleton, request context/scoped access/transaction seam, shared logic (business date, ids), UI contract/tokens, i18n seam, test seam, read model. All of it was derivable from the SAD from the start — the initial backlog jumped straight from scaffold to features. The criterion that separates it from YAGNI: *"would inserting it later force rewriting feature code that is already merged?"* — yes ⇒ foundation, do it right after scaffold; no ⇒ it can wait | The "Foundation pass" step in LOOP.md's standard flow |
| L14 | The first real `/loops:update` run: LOOP.md declared itself `managed` but the Foundation pass checklist had been **legitimately localized** to each repo's SAD → every later diff became a false conflict. A file with a generic part + a per-repo part has to be `mixed` with markers; do not force it to `managed` | LOOP.md switched to `mixed` (core/rituals block); the foundation checklist sits outside the markers and belongs to the repo |
| L15 | The failure class "generated but never wired in": **7 cases in a repo 6 days old** (contract-test scaffold, MSW handlers, CI workflow, recompute function, scoped repository, the loops-check script itself, invalidation constants) — complete artifact, its own tests green, doc written in the future tense → reads as done, but **0 import edges, so it never ran**. Grepping for stub markers does not catch it: what is missing is an edge in the import graph, not file content. When stories are split by package, producer and consumer always sit in two different stories — the connecting edge belongs to nobody by default | templates/story.md "Story closing checklist" section; /loops:next done condition #4 (consumer edge) |
| L16 | A gate existing in the repo ≠ a gate actually blocking broken PRs (not enforced), and besides `continue-on-error` there are 3 more forms: a CI workflow the remote never reads (GitHub Actions YAML on a GitLab remote — "hasn't run because it hasn't been pushed yet" sounds reasonable enough that nobody checks), a check script no hook or job calls, an integration suite outside the `test` target that only runs when someone remembers to type it by hand | LOOP.md maintenance rule 8 (a new gate declares its call site in the same PR); /loops:next extended "gate not enforced" list |
| L17 | A review finding does not turn into a change by itself: the same finding was caught again by two independent reviews (3 days apart) because nobody turned it into a diff the first time. Review only produces prose when a finding is allowed to sit in a fourth state, "acknowledged" | /loops:review Step 3: every finding closes in exactly 1 of 3 states (fixed / has a story / rejected by a human with a reason); the next review checks follow-through first |
| L18 | Operational docs (wave kick-off prompts, temporary setup guides) rot fastest of the whole doc set: an expiry condition written in words ("delete when Wave 1 closes") that nobody checks, so the file lived on for days after **every** instruction in it was wrong, directing agents to redo work already Done | /loops:review sweep has the item "operational doc past its expiry condition"; this kind of doc has to declare a machine-checkable expiry condition (a list of story IDs) |
| L19 | An approved number does not propagate by itself: the estimate "~988" lived 3 days after "968" was finalized — even in a doc edited AFTER the decision date. An approval that carries a number without grepping the old value down to 0 in the same PR leaves the repo with two sources of truth alive at once | LOOP.md maintenance rule 9 (grep the replaced value down to 0, except changelog/snapshots); /loops:review sweep |
| L20 | A log replayed from the build cache reads exactly like a real run (turbo/nx reprint the old output verbatim, test names included) — a reviewer nearly accepted 15 "green" tasks that were all cache hits as acceptance evidence | /loops:review Gather section: acceptance evidence = a 0-cache/`--force` run; look at the `Cached: X/Y` line before believing it |
| L21 | **A shared file nobody owns is where parallel sessions overwrite each other's edits.** project B 2026-08-16: two sessions clobbered each other **three times in one day** in exactly the two files every story has to touch — the backlog table and TEST_MATRIX. The first fix was one sentence of rules in AGENTS.md ("only edit your own row, no `git add -A`") — exactly the failure class L8 had warned about: a rule in words does not hold. What holds is structure: the two tables become **generated artifacts** built from story front matter (`loops-gen`), nobody edits them by hand, `loops-check` fails when they diverge. Alongside: a story declares `owns` (glob paths it edits) and the check fails when two active stories overlap — the conflict surfaces **before** two sessions run together, not at merge time | `scripts/loops-gen.mjs`; `owns` front matter in templates/story.md; loops-check item 7 |
| L22 | **A story packet carries three roles at three writing cadences** — the contract (scope/AC), the design with its decisions, and the acceptance log appended at the tail. Project B's ST-018 ran 370 lines, with 5 OPENs resolved right inside the file and the last 90 lines being "ran it and saw X" for 6 lands. Measured consequences: (a) an agent opening the story has to read all three layers; (b) decisions that outlive the story (admin whitelist via ENV, LLM provider abstraction, computing onTimeRate by replay) **are not in any ADR**, so a later agent reading only ADRs will not see them; (c) the 2026-08-15 baseline review, F1: the story said "Ready" while OPENs that block implementation were still sitting further down, because the OPENs were buried in the file body. Split by cadence: packet = contract with a line budget (250, machine-enforced like AGENTS.md); questions → one `OPEN.md` queue in one place, the PO answers them in one sitting, and a story with an unresolved OPEN cannot be set Ready by the machine; acceptance evidence → PR description | templates/story.md (`opens` front matter, budget); `docs/decisions/OPEN.md`; /loops:land Step 5 |
| L23 | **Waves written by hand in a review doc are the fastest-rotting kind of operational doc (L18) and do not catch cross-dependencies.** The 2026-08-14 foundation plan laid out waves in prose; the 2026-08-15 review had to discover on its own that ST-005 and ST-006 both edit `verify.yml` in the same wave (F3), and that ST-007 needs ST-009's `apps/web` from a later wave (F4). Both are mechanically derivable if stories declare `depends_on`/`consumes`/`owns`. From v0.5.0 waves are no longer written: `/loops:wave` computes the Ready set with disjoint `owns` from front matter on each run, and emits a self-contained start prompt per session (replacing the "wave prompt" doc that L18 had already seen giving wrong directions after a few days). Side lesson: `/loops:next` returns **one** piece of work, by design, for one agent — parallelism needs its own skill, not a loosened old one | /loops:wave; `depends_on`/`consumes` front matter; /loops:start, /loops:land |
| L24 | **Consistent docs do not prove that the code matches the docs, and that gap holds the most expensive bugs.** The project B technical review of 2026-09-04: the repo passed every harness gate clean (`loops-check` OK, generated tables not diverged, 13 ADRs consistent, TEST_MATRIX with no fake ✅, 1,155 tests green with cache off) and still had 6 confirmed behavioral bugs, 2 of which broke exactly the invariants backed by an ADR. The clearest example: ADR-0009 declares idempotency keyed on `(user_id, client_id)`, with a test, with a gate — the client generates a fresh `client_id` on every retry, so the keys never collide; the gate runs correctly and deduplicates nothing. This failure class differs from L15 (missing import edge) and L16 (gate not blocking): here **there is an ADR, there is a test, there is a gate, and the code still violates it on a branch nobody listed**. No doc contradicts any other doc, so a docs pass never sees it | /loops:review Step 2 (code reality pass); LOOP.md review ritual; templates/review.md section 6 has ADR ↔ code pairs |
| L25 | **An "evidence of what ran" section grew on its own in every real review** — both the 2026-08-18 and the 2026-09-04 reviews of project B spawned a §0 section as a command/result table that the template did not have, because without it "ran it and saw X" mixes with "inferred X from the code" and the whole report loses its acceptance value. Same pattern as L4: what grows back every time belongs in the template. Alongside: this section is the only place that turns L20 (log replayed from cache) into something checkable, because it requires writing the `Cached: X/Y` line verbatim and requires listing **what did not run** — leaving the latter blank lets the reader infer "everything was green" | templates/review.md section 0 (VI + EN); /loops:review Gather section |
| L26 | **The harness shipped `loops-check.mjs` for four consecutive versions with a comment line "wire it into CI" and shipped no call site** — i.e. it was itself the L16 case it warns about, and every repo that installed the harness inherited a gate nobody calls. An instruction in words for a human is not a call site. The fix is to make the script ask that question about itself: scan the hook config and the CI config for an invocation, and fail if there is none, with dependency-free instructions (`.githooks/pre-push` + `core.hooksPath`). A script in `package.json` deliberately does NOT count — an alias is only a shorter way to type it, not the thing that runs it | loops-check item 9; /loops:init Step 3.7 (installing the hook is mandatory, not advice) |
| L27 | **Reviewers given parallel work report the right content with the wrong coordinates.** The 2026-09-04 review was split among 4 agents reading 4 disjoint areas: one agent reported `streak.service.ts:170` (the real line is `:147`), one quoted a file `features/review/reviewSink.ts` that does not exist (the real one is `api/reviewSink.ts`). One wrong coordinate makes the fixer open the wrong place and conclude the whole report is made up, so a finding from another reviewer is PLAUSIBLE until the lead opens the right line themselves — that is the lead's real job, not a formality. Second rule: **reviewers do not run the gates**; the lead runs them once with `--force` and hands out the result; otherwise each reviewer builds on their own and reads a cached log again — L20 multiplied by the number of reviewers | /loops:review Gather section (splitting the read); templates/review.md CONFIRMED/PLAUSIBLE labels |
| L28 | **The harness's checks have no time axis.** Every check reads the repo as a snapshot, so it cannot see what is rotting on the calendar: project B's OPEN-003, open since 2026-08-22, came with its own proposed deadline "after 30 days, enable the 2 GitLab jobs" — the deadline passed, nobody owned it, 15 TEST_MATRIX rows sat at 🟡 because of it; and 12 stories moved to done since the last independent review with nothing measuring the review debt. Both are machine-measurable if the OPEN table has a date column. It is a **note, not a failure**: blocking push because someone is slow to answer punishes the wrong person | loops-check item 10; the "Opened" column in decisions/OPEN.md; loadOpens reads by column name |
| L29 | **An "out of scope" clause with a reason is a technical claim nobody has checked — and it gets written so that no test has to be.** ST-017 (🔴, done) excluded the UPDATE branch of `recordWatering` from scope with the reason "two transactions on the same `day` compute the same value, the later write overwrites with the same value, not wrong". True for the same day, false for an older day — and F3 of the 2026-09-04 review sat exactly on that branch: a late offline flush reset the streak to 1 and then wrote `last_reviewed_business_date` backwards. The bug sat exactly where the story had convinced everyone it was safe. Distinguish two kinds of exclusion: "another story takes it" is a hand-off; "not needed because X" is an assumption and has to be written in a verifiable form or get its own story | templates/story.md Scope section; /loops:review Step 1 (re-read the Out-of-scope clauses of done stories in the area under review) |
| L30 | **In a repo, what can be recomputed and what is gone for good look identical.** project B's ADR-0002 declares `review_logs` the single source of truth that cannot be recomputed; after 24 days and 159 commits there was still no backup, because the story that owned that work was frozen after an unrelated CI decision. No doc contradicts any other doc — "the ADR says it matters" + "nobody has backed it up yet" is a state a docs-reading review never sees. Only the ADR knows which tables cannot be recomputed, so the ADR itself has to declare where the backup runs and when the last restore was | LOOP.md maintenance rule 11; /loops:review Step 1 |
| L31 | **A hand-written YAML parser rejected valid YAML input with a message that reads like a corrupted file.** A long `owns` gets broken by the formatter (or a person) into a multi-line flow list — perfectly valid YAML — and `loops-gen`'s subset parser returned `cannot parse "  ["`, which reads like broken front matter rather than an unsupported form; `loops-check` went red without saying what to fix. And the harness is the thing that *requires* `owns` on every in-progress story, so it produces that input itself. A small subset is fine, but the error message has to name the accepted forms, and any form the harness generates itself has to parse | loops-gen `parseFrontMatter` (4 list forms + a message naming the shape) |
| L32 | **`owns` is only ever compared between stories, never against the real diff.** The anti-clobber check (L21) answers "do two active stories step on each other", so a story editing a file it never declared stays perfectly green — a wrong declaration only shows when the second session runs, which is exactly when it is too late. Project B 2026-09-04: the commit closing ST-024 touched 100 files, of which **11 belonged to the `owns` of no active story** (`packages/api-spec/**` + the regenerated client, 3 screens under `apps/web/src/features/**`, `pnpm-workspace.yaml`, `AGENTS.md`, the runbook). Nobody's edits got overwritten because only one session was running at the time — that is luck, not a gate. Fix: compare the set of changed files (uncommitted + committed-not-pushed) against the union of `owns` of the active stories. It is a **note, not a failure**, because there are always repo-wide files no story owns, and a failure in the wrong place gets worked around instead of fixed | loops-check item 11 |
| L33 | **An "in progress" status written in a file on the story branch is invisible to other sessions.** `/loops:start` commits `status: in-progress` on the story branch, reasoning "that is what tells other sessions the path is taken", but `loops-check` and `/loops:wave` only read the working tree of the checkout they are standing in. Trial repo 2026-09-28: after ST-001 started in its own worktree, the main checkout still showed ST-001 as `☐`/ready and `loops-check: OK`; running `/loops:wave` again would hand ST-001 to a second session. What every worktree of one clone sees is the branch ref. So a story is active = `in-progress` **or** has an unmerged `story/ST-xxx` branch. Both halves are needed: in project B, ST-012 was still `in-progress` on main while the branch of land 1 had already merged. A side consequence: `ready` no longer means "path claimed", so two `ready` stories with overlapping `owns` is only a note — before, the check failed there, so the step in `/loops:wave` that chooses between two overlapping candidates was never reached | loops-gen `loadClaims` + `--claims`; `isActive`; loops-check item 7; /loops:start steps 2–3; /loops:wave steps 1–2 |
| L34 | **Two stories that never touch each other's paths still always conflict at merge — in exactly the two tables generated to prevent conflicts.** Each story branch regenerates `docs/stories/README.md` and `TEST_MATRIX.md` and commits them (/loops:land step 4), so from the second merge on both files conflict (trial repo 2026-09-28, `owns` `apps/a/**` and `apps/b/**`). Running `loops-gen` while in conflict resolves all of it, but no doc said so, and resolving the generated block by hand is exactly what L21 forbids. Fix: the rule "resolve the conflict in the story file, then run loops-gen" in /loops:land and stories/README; `loops-check` fails while conflict markers remain in a generated table. A merge driver in `.gitattributes` was not used: it needs `git config` on every clone, i.e. the same problem as `core.hooksPath` all over again | /loops:land step 4; stories/README; loops-check item 7 |
| L35 | **The "has a call site" check only looks for the script name in files, so it accepts things that never run.** Trial repo 2026-09-28, all four cases printed `invoked from:`: `.githooks/pre-push` with `core.hooksPath` not set (git does not run it), a Makefile target (an alias, like the `package.json` script this item deliberately excludes), a comment line `# TODO: run loops-check`, and a GitHub workflow in a repo that also has `.gitlab-ci.yml`. Guessing GitHub/GitLab from the remote URL is not an option: both the predecessor harness repo and project B use a self-hosted host, so that approach would fail wrongly on exactly these two repos. So fail only on the certain cases (a hook git does not run, a comment); the Makefile and the two CI systems are a note | loops-check item 9 |
| L36 | **"Done checked by machine" only checks the ✅ marks the person closing the story typed themselves, not whether any test runs.** Trial repo: story `done`, proof `unit` ✅, the repo has no test file at all → `loops-check: OK`. Project B 2026-09-29: 20 proof rows at ✅ (not counting `manual`) with no test file mentioning the ID. Fix at note level: require the ID to appear in the test name so a reviewer can find the test. Not a failure, because older repos would go red the moment they bump the version, and a test name is only a convention — it does not prove the test checks the right behavior | loops-check item 8b; templates/story.md; /loops:land step 1; LOOP.md definition of Done |
| L37 | **A hook proven by piping JSON into it is not a hook proven in a session.** Every loops hook had a fixture (JSON on stdin → exit 2 / JSON deny) and the self-review listed "hooks in a live session: not observed" as an unverified assumption. The first live `claude -p` run on a lab repo's runbook (2026-10-06, Claude Code 2.1.290, Windows 11) edited a file outside `owns` and reported "no hook blocked it". Claude Code's debug log held both causes: hook commands run under PowerShell there, so `$CLAUDE_PROJECT_DIR` was `$null` and the path became `C:\.claude\hooks\…` ("Cannot find module", status 1); and with the path fixed, a hook that exited 2 was logged as "status code 1" because PowerShell reports any failing native command as 1 — and a hook that errored never blocks. Only the JSON form (`permissionDecision: deny`, exit 0) blocked, and its reason reached the model. Fixes: every hook blocks through `deny()`; settings write `${CLAUDE_PROJECT_DIR}` with braces; `loops-check` item 13 fails on the unbraced form; the runbook's live-session step is the proof that stays | hooks/lib.mjs `block()` → `deny()`; template/.claude/settings.json; loops-check item 13; docs/decisions/README.md drift note on ADR-0004 |
| L38 | **A step only a skill sentence performs is skipped the first time someone runs the script directly.** `/loops:update` Step 3 said "set LOOPS_VERSION by hand"; on 2026-10-15 the updater was run from the shell on the loops repo and on project C, and both were left with a stamp one version behind the manifest (`release.mjs` ✗, `loops-check` note blaming a hand edit). The script that writes the manifest version now writes the stamp in the same run. Two side findings from the rerun: a literal slot in a managed script makes the merge stage it as a conflict with "0 conflicting region(s)" (now named, and T-UPD-8 forbids it); and an update that changes the updater runs the old copy, so that one update needs a second `apply`. Remove `stampVersion` when the stamp moves inside a LOOPS block. Record: docs/reviews/2026-10-15-improve-update-stamps-version.md | loops-update.mjs `stampVersion`, `whyConflict`; skills/update Step 3; test/update.mjs T-UPD-7, T-UPD-8 |

## Known limits of the harness (not solved by docs)

- **Scope estimation:** the number 1 risk the cross-review found was a roadmap ~50% too optimistic — the harness has no mechanism to catch this other than the cross-review itself. Accepted: this is human work when approving stories/the roadmap.
- **TEST_MATRIX scale:** from v0.5.0 the main block is generated from `proof` in story front matter (L21) — the remaining limit is that the markdown table is still something people read, not the source the machine runs tests from; linking `proof` ↔ real test tags is still not done (YAGNI until a project is big enough).
- **Humans are still the sync bottleneck:** `OPEN.md` collects questions in one place so they can be answered in batches, but it does not shorten the PO's thinking time. Many parallel sessions are only faster when the PO resolves OPENs on a cadence — /loops:wave reports when the set blocked by OPENs is larger than the runnable set; the rest is human work.
