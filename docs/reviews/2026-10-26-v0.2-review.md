## 3. Findings — SEVERE

### F1 · A repo with no stored base gets no upstream change and is stamped current — CONFIRMED

`planFile` uses `base ?? upstream` (`template/scripts/loops-update.mjs:102`); `merge3` then short-circuits on `base === upstream` and returns LOCAL with 0 conflicts (`:77`), so the "no stored base … shown against upstream" conflict at `:104` can never be produced. `commitPlan` then records the new upstream as base (`:139-152`), after which the repo looks up to date for good. `skills/update/SKILL.md:32` (Step 0a) tells the agent to run `init` against the current plugin and promises "every local edit will show as a conflict against upstream"; `init` records upstream as base, giving the same no-op. Repro 0a: `applied 0 file(s)`, `status` → `current`, while both an untouched and a locally edited file kept the old text. This is the path Step 0b prescribes for every repo on the predecessor harness — project B included.

- **Recommendation:** ST-015 — when a file has no stored base and LOCAL ≠ UPSTREAM, stage it as a conflict (base side empty), and make `init` on a repo whose files already exist record a base only for files byte-equal to the template; fixture for both.

### F2 · A mixed file with one conflicting block drops the other blocks' upstream changes for good — CONFIRMED

The mixed branch of `planFile` returns on the first conflicting block (`template/scripts/loops-update.mjs:118-119`): blocks already merged in `text` are discarded and later blocks are never examined, so only one block per file is ever staged. `--continue` writes that one block and `commitPlan` records the whole new template as base. Repro A: `docs/LOOP.md` lost the `rituals` change; a second `apply` after commit reported nothing to do, because `rituals` now has base = upstream. Affected files today: `AGENTS.md` (2 blocks), `docs/LOOP.md` (2 blocks). This breaks ADR-0005 point 3 ("all or nothing") without any message. T-UPD-5 covers only a single clean block.

- **Recommendation:** ST-015 — plan every block of a mixed file, stage each conflicting block under its own `path#block` name and carry the clean ones in `merged/`; fixture with two blocks, one conflicting.

## 4. Findings — MEDIUM

### F3 · `REVIEW.md` is listed as `mixed` but has no marker block, so it is never updated — CONFIRMED

`loops-install-files.txt:38` lists `mixed REVIEW.md`; `template/REVIEW.md` has no `LOOPS:BEGIN`. `planFile` iterates the template's blocks (`loops-update.mjs:113`), finds none, returns `unchanged`. Repro C confirms. ST-005's checklist says REVIEW.md was listed "(managed)". Nothing checks that a `mixed` file carries at least one block.

- **Recommendation:** ST-015 — wrap the loops-owned part of `template/REVIEW.md` in a marker block (the "Do not report" list stays the repo's), and add a fixture that fails when a `mixed` template file has no block.

### F4 · `stage-guard` blocks on every branch and in every directory, including text inside a heredoc — CONFIRMED

`template/.claude/hooks/stage-guard.mjs:7-18` never reads the branch. AGENTS.md ("On a `story/ST-xxx` branch, … `git add -A` / `commit -a` are blocked") and ST-004's AC ("names the story-scoped staging rule") describe a story-scoped rule. Observed twice in this session on `main`: a `git add -A` inside a throwaway repo under the system temp dir was denied, and so was a heredoc that only *wrote* a script containing `git add -A`. The message asks for "this story's owns" when there is no story.

- **Recommendation:** ST-016 — return early unless `currentBranch(repoRoot(input))` matches `story/ST-\d+`, as `owns-guard` does; fixture for main and for a story branch.

### F5 · Carried from v0.1 F5: the agent configuration is still unproven — CONFIRMED

`evals/last-run.md`: one phrasing run (2026-10-06), 0/1 passed, 4.09 USD. The manual proofs T-SKL-4…8 and T-DOC-4…6 are ✅ on reading, not on a run. v0.1 action 3 was tagged "[next milestone]"; the milestone closed without it. OPEN-004 (run `--bare` before touching the cost cap) has waited 20 days and blocks no story, so no queue shows it as anyone's next step.

- **Recommendation:** ST-017 — run the suite once under OPEN-004's answer and commit `evals/last-run.md`; the story lists `opens: [OPEN-004]`, which makes the decision visible in the backlog's "Blocked by" column.

### F6 · File writes through Bash route around `owns-guard` — PLAUSIBLE (decision required)

`owns-guard` is wired only on `Edit|Write|MultiEdit|NotebookEdit` (`.claude/settings.json`). ST-004 put a Bash matcher out of scope "added only if dogfood shows agents routing around". This session's own runtime instructions (Claude Code auto mode) tell the agent it may "make small, mechanical file changes with sed, heredocs, or short scripts", so routing around is now the default suggestion, not an exception. The fallback, `loops-check` item 11, is a note and exempts `docs/decisions/**` entirely (`template/scripts/loops-check.mjs:486`). Not exercised on a story branch in this pass.

- **Recommendation:** an `/loops:improve` experiment (one story-branch session in auto mode, count Bash writes outside `owns`) before adding a matcher. Whether to spend that run is the owner's call.
